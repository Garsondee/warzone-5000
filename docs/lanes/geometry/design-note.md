# GEOMETRY design note (settling round)

**Purpose.** One closed, tagged, measured geometry feeds the look, the mass, the armour and the collision. Vehicles are built from parametric parts (card C-004: never hand-modelled), so every generator takes numbers and returns a part. Evidence for the flag decisions: `spike-g.md`. CCRs: `docs/swarm/requests/geometry-ccr-shapes-and-tracks.md`.

## 1. Pipeline of one part (pure function of its parameters; f64 inside, f32 once at export; ordered iteration, no `HashMap`)
`template (RON, normalised) + Params (metres) -> sections -> loft / extrude / bevel -> weld -> checks (closed, outward, no sliver) -> Part`. Then, for a whole vehicle in its design pose: `edge` per part, `cavity` on the assembled set, `f32` buffers, `MeshPart`.

## 2. Flags (decisions; spike S-G)
- **`edge`**: convex dihedral only, ramp 20 to 70 degrees, concave 0, vertex = max of its edges. `PROVISIONAL(status:geometry)` until LOOK agrees; the three numbers are `Param`s with provenance ESTIMATE ("looks right on a chamfer", band 10 to 30 and 55 to 85 degrees).
- Generator rules that make it work: one inset loop per hard edge at the band width (default 5 cm, ESTIMATE); a vertex at least every 0.5 m on a hard edge so corner values do not run along it; hard-edge loops are budgeted separately (a CI check: loops under 25% of a vehicle's triangles; measured at build step 6).
- **`cavity`**: cosine-weighted Hammersley rays, cap 0.5 m, origin lifted 0.5 mm (ESTIMATE), baked on the assembled vehicle in its design pose, BVH, one thread. **Default 256 rays** (3.1 s for 30k triangles; 1024 is 11.6 s and breaks the 10 s kill line, so 1024 is for the oracle tests only).

## 3. Mass API for FORGE (`w5k_geo::mass`, build step 1)
```rust
pub struct MassProps { pub volume_m3: f64, pub centroid_m: Vec3, pub second_moment_m5: Mat3 /* about the centroid, density 1 */ }
impl Mesh { pub fn mass_props(&self) -> MassProps; pub fn shell_props(&self, thickness_m: f64) -> MassProps /* thin shell for armour */ }
impl MassProps { pub fn translate(&self, d: Vec3) -> MassProps; pub fn rotate(&self, r: &Mat3) -> MassProps; pub fn scale(&self, s: f64) -> MassProps /* V s^3, I s^5 */;
                 pub fn sum(parts: &[MassProps]) -> MassProps /* parallel-axis */; pub fn at_density(&self, kg_m3: f64) -> (f64 /*kg*/, Mat3 /*kg m^2*/) }
```
Unit-density means FORGE multiplies by a density (or scales to a stated mass: mass = density x volume, so a stated mass fixes the density). Exact for the mesh as meshed (divergence theorem, no sampling); tests A2 and A3. `shell_props` is the same sum over triangles with area instead of volume, for COMBAT's armour in M3; I will build it only when asked.

## 4. Part API
```rust
pub struct Part { pub name: String, pub role: NodeRole, pub station: Option<u8> /* axle or road wheel index */, pub side: Side /* Left, Right, Centre */,
                  pub slot: SlotKind, pub fitting: bool /* mirrors, handles: not in the hull box */, pub mesh: Mesh }
pub fn build_vehicle(shapes: &ShapeSet, detail: u8) -> Vec<Part>;     // ShapeSet from the defs (CCR a); a hull-frame, design-pose set
impl Part { pub fn to_mesh_part(&self, node: usize, slot: usize) -> MeshPart }   // the one f64 -> f32 conversion
```
FORGE builds the nodes (hull > travel > steer > wheel, one `Track` node per side) and maps `(role, station, side)` to a node index. Wheel parts are in the wheel node frame, hub at the origin, axle along local X; the hull parts are in the hull frame.

## 5. Where shape parameters live
Normalised shape templates (RON, `include_str!`) in `crates/w5k_geo/shapes/`: station sections as fractions of length, width, height, which is how a loft is authored (a ship's lines plan). Real dimensions come from the `VehicleDef` as `Param`s; a shape number the dossier lacks (glacis angle, bevel, sponson depth) is an ESTIMATE with a band and a reason, carried in `ShapeDef` (CCR a). Nothing physical is typed in Rust.

## 6. Datum, ride height, dimensions (to agree with FORGE; `PROVISIONAL(D3)`)
Hull frame origin = the centre of the **hull box** (FORGE's D3), +Y up, -Z forward. Hull box = the bounding box of the `Hull` parts with `fitting == false`, greenhouse included, mirrors, aerials and tow hooks excluded; `HullDef::length_m/width_m/height_m` mean that box and A10 prints which definition matched. Ride height = clearance + height / 2, from FORGE; wheel bottoms touch -ride_height within 1 mm (A8). VALIDATION decides what a dossier's "height" includes; GEOMETRY follows and says so in the test output.

## 7. `detail` and the budget
`detail: u8` = 0 coarse (24-gon wheels, no tread blocks, fewer loops), 1 default (48-gon), 2 reference (128-gon, tread, full loops). It scales circular segment counts and loop rings only; shapes and masses do not change except by the 1.0 mm sag limit at level 2. Level 2 is what A8 tests (sag R (1 - cos(pi/N)) = 0.4 m x 0.0003 = 0.1 mm at N = 128). It is a tessellation level for LOOK's LOD test, not a LOD system. Budget as in the brief: wheeled 50k triangles (the owner raised it from 40k on 2026-10-10; it is stated once, as a `Param` in `shapes/budget.ron`, and the tests and the tool message read it from there), tracked 80k with instanced links counted once, 30 draw calls; the real numbers come at build steps 6 and 7 and VIEWER's software-GL timing.

## 8. The hull is one shell, and everything else is anchored to it (owner feedback 2026-10-10)
The first truck was a heap of separate boxes: windows, mirrors and bumpers floated off the body and each mud guard was a slab lying on its wheel. The rebuilt hull (`truck.rs`, `shapes/utility_4x4.ron`) follows three rules.
- **One skin.** The shell is a single loft along the length. Each section is a T-shaped ring: a full-width lower body (bottom to belt line) with a narrower hood, cab or bed block on top. The **wheel arches are openings cut into the section**: at the wheel stations the lower outer corners of the ring are notched, and the notch height follows the wheel circle (`sqrt((R + gap)^2 - dz^2)`), sampled at 12 extra sections per arch. A lip, swept around the arch circle (`sweep_arc`), stands proud of the wall, so the mud guard wraps over and down both sides of the tyre and flows into the body.
- **Anchors, not coordinates.** A fitting is placed relative to a surface of the shell: `Upper` / `Lower` (metres from the walls), `Belt` / `Top` (from the belt and roof lines), `Front` / `Rear` (from the end faces), and it overlaps the surface by a couple of centimetres. Glass follows the roof line (`Pane`, `Windscreen`), panels follow the top line (`Overlay`). Changing the dimensions moves the surfaces and the fittings with them.
- **A test says so.** `every_fitting_is_embedded_in_the_hull_or_in_a_fitting_that_is` (volumes must overlap, chained through the mirror arm and handle), `plates_and_glass_hug_the_shell_within_3_cm` and `wheels_clear_the_shell_and_the_arches_open_over_every_tyre` fail the build when something floats or a wheel pokes through; the 200 random in-range sets still close every part.

Why not boolean operations? Cutting an arch out of a box needs a mesh CSG kernel (robust intersection, tolerance handling), which is a project of its own and a determinism risk. Cutting the arch into the *section* costs nothing: the loft already interpolates between sections, so the notch height is just one more number per station.

**Vertex rows for the flags** (spike S-G, applied along the length): `loft_beveled` gives every part a chamfered end, an inner ring `band` further in (so the end face has a zero-flag interior), repeats the ring `bevel` and `bevel + band` from each end, and adds a row `band` either side of every crease station. Without them the `edge` flag smeared across large faces as clouds. Costs: the truck is about 36k triangles of the 40k budget (subdivision edge 0.4 m; 0.3 m gave 41.8k). `triangulate_ring` (ear clipping with collinear points put back by fanning) caps non-convex end rings, so the T-shaped nose face closes.

### 8a. Glazing and silhouette (owner feedback 2026-10-10, second round: "the windows need to conform better", "the front side window and the front top must line up")
- **Glass is a panel set into the wall with a frame.** A window is a flat panel (`panel`: an outline with chamfered corners, extruded a few millimetres) lying on the wall plane, plus a raised bezel swept around its outline (`sweep_loop`, mitered, 12 to 14 mm proud): the frame stands above the glass, so the glass reads as recessed. The upper walls lean inward (`tilt`, the tumblehome, about 6 degrees on the cab) and the pane is sheared onto that plane.
- **The two angles are one angle.** The front side window's slanted edge is the roof-line ramp (the windscreen's plane seen from the side) moved `pillar_m` into the cab, square to itself, then cut by the sill line and the top line (`PaneFront::Pillar`), so it is parallel to the windscreen by construction. The test `the_front_side_window_leans_at_the_same_angle_as_the_windscreen` measures both in the side view (a principal-axis fit of the windscreen, the longest slanted hull edge of the window) and requires them within 0.75 degrees; before this change the window's slanted edge was its top edge (a chord across the roof kink) at about 23 degrees against a 45 degree ramp. The ramp itself is now about 58 degrees from horizontal (an upright utility-truck windscreen).
- **Silhouette.** The underside rises towards the nose and tail (`yo` per station: approach and departure ramps) and each arch lip ends where its arch meets the local underside; the hood front slopes down to the fender deck (stations 0 to 2); the sill is tucked by a 9 cm chamfer (`sill_chamfer_m`); the canvas cover slopes down towards the tail; the cowl widens into the cab over 6% of the length instead of 3.5%.
- **Dimensions are now M998-class** (`placeholder_utility_4x4.ron`): 4.572 x 2.159 m, 1.79 m ground to roof (hull box 1.37 m above a 0.42 m clearance), wheelbase 3.302 m from the dossier; track 1.82 m and the 0.82 m x 0.30 m tyre from the Mule, so the skin still sits on the Mule's rig. The test `utility_4x4_dimensions_match_the_m998_dossier_within_3_percent` (A10 for the HMMWV) reads `content/dossier/m998.ron` and prints which definition matched (length and width over the non-fitting hull parts, height ground to roof, clearance ground to underside).
- **Picture tool bug found on the way:** `raster.rs` interpolated depth linearly in screen space, which is wrong under perspective (1/z is what varies linearly); on a large triangle the error exceeded the 3 mm the glass stands proud and the shell showed through in specks. Depth and the flags are now interpolated with weights l_i / z_i.

## 9. Modules and sockets: a vehicle is a hull, running gear, a weapon mount and a weapon (owner goal 2026-10-10)
The audit of the first truck: it is parametric (dimensions drive the shape, the shape is RON data, fittings are anchored) but not modular: `utility_4x4()` builds hull, wheels and knuckles from one hard-wired template, two axles are baked into the arches and the export, and there is no mount or weapon at all. The goal is a separate hull, separate propulsion, a separate weapon mount and separate weapons, as in the archived prototype's part forge and brief card C-004. `module.rs` is the joining kernel; the families that use it follow.
- **Module.** Parts in the module's own frame, the **sockets** it offers, and (if it can be attached) one `mount` socket. Nothing in `module.rs` knows what a hull or a gun is.
- **Socket.** A frame (position, outward normal = local +Y, reference direction = local -Z), a kind from the standard vocabulary (`Station`: a wheel or road wheel position on a side of the hull, size = largest wheel radius; `Ring`: a turret or mount ring, size = diameter; `Trunnion`: a weapon pivot, size = cradle width), a side and named hints (room along the hull, wall to keep clear of). The vocabulary grows with the families (keel, belly, mast, engine bay, track run).
- **Fit.** Two sockets fit when the kinds are equal and the child's size does not exceed the parent's. The child's mount frame goes on the parent's socket frame with the normals opposed and the references together (half a turn about the socket's Z axis), then an optional `spin` about the normal. A refusal (unknown or taken socket, kind mismatch, oversize, no mount) leaves the assembly untouched and says why. Physics, not rules, decides whether a legal combination is any good (mass, balance, recoil).
- **Left and right.** A module that is not its own mirror image is mirrored (meshes, part frames, sockets, mount, part sides) before it goes on a left socket, so one authored wheel serves both sides and stays upright.
- **Articulation.** A part of a module with role `Hull` is baked into the hull frame (a collar, a fixed housing); every other role keeps its mesh in its node frame and a pose in the hull frame (turntable `Turret`, `GunPitch`, `Recoil`; wheels). The caller labels each placement and every part and socket of the module becomes `<name>.<label>` (`tyre.0.r`, `trunnion.ring`), so names say where a thing is, a name already in the assembly is refused, and a weapon attaches to the mount's `trunnion.ring` with the chain resolving in the hull frame. Parts with no axle index of their own take the `Station` socket's.
- **Hull and running gear, built (modules PR 2).** `truck::utility_hull(d, axles_z, detail)` is the hull module: the shell with an arch cut for every axle it is given, the fittings and lips, and one `Station` socket per wheel position (`station.<axle>.<r|l>`: at the hub, normal outward, size = the wheel radius the arch was cut for, hints `well_x_m`, the x of the wheel well's inner wall, and `max_width_m`). `gear::wheel_module(w, segments, knuckle)` is the wheel (tyre, tread, rim, nuts, and a steering knuckle on a steered axle), authored for the right-hand side with its mount facing the hull, so on an axis-aligned station it needs no rotation (the left wheel is its mirror). `truck::utility_truck(d, axles_z, steered, detail)` is the recipe that attaches one wheel module to every station; `utility_4x4` is that recipe with two axles. The knuckle's reach is computed from the station's hint, so the gear reads what the hull published and the two share no code. **Proof of a pure refactor:** the golden hash (names, node-frame meshes, indices) did not change, and the exported `RenderRig` JSON, the GLB and the dimension table are byte-identical (sha256) to the monolith's. Three axles work (`utility_truck` with a tandem: six arches, six wheels, two knuckles, wheels clear the shell: `three_axles_cut_three_arches_take_six_wheels_and_two_knuckles_and_the_wheels_clear_the_shell`); pictures `media/modules-propulsion-*.png`. The 6x6 picture of this step had a flaw (the sill step ran across the middle arch) that the regions of the last step fixed.
- **Weapon mount, built (modules PR 3).** The hull offers a `Ring` socket on the cab roof over the hatch, defined in the hull's RON by the part list's anchors (`x: Frac`, `y: Top(-0.02)`, `z: Frac(0.59)`, size 0.90 m, normal up, reference forward; 2 cm into the roof because the roof rises a degree along its length, so a level collar always touches it). `mount::ring_mount(dims, detail)` (`shapes/ring_mount.ron`) is the module that goes on it: a stepped collar (role `Hull`, a fitting, so it is not part of the hull box that dimensions measure), and a turntable, two cradle uprights and two swept shield wings (role `Turret`, one node frame at the centre of the collar's top face). It mounts on a `Ring` socket sized by its ring diameter (a 1.2 m ring is refused on the 0.9 m roof) and offers a `Trunnion` socket at the cradle, sized by the cradle's clear width with the width as the hint `cradle_w_m` for the gun to read. `truck::utility_assembly` returns the truck as an assembly so the caller attaches what it likes. The mount costs about 1.3k triangles in the rig (37.3k of 40k); small hardware comes from `hardware.rs` (bevelled boxes with the flag bands scaled down to the part, cylinders on any axis, a surface of revolution about Y).
- **Weapons, built (modules PR 4).** `weapon::gun_module(dims, cradle_w_m, detail)` is one parametric gun generator with presets in `shapes/weapons.ron` (`machine_gun_12_7`, `autocannon_25`; a preset is a handful of sliders: receiver box, barrel length and radius, an optional jacket, a muzzle device, ammunition boxes (one, or a mirrored pair), spade grips or a sight). A gun is authored in its own frame (trunnion axis at the origin, bore along -Z) and mounts on a `Trunnion` socket by a mount of its own (normal back, reference up, so on the mount's forward-facing trunnion it needs no rotation); the size of that mount is the receiver's width, so a cradle takes it only if the receiver fits between the uprights. The trunnion pins read the hint `cradle_w_m` and are exactly long enough to end inside the uprights. Roles: receiver, pins, boxes, grips, sight swing with the gun (`GunPitch`); barrel, jacket and muzzle device slide back on firing (`Recoil`). The swap test proves the separation: with either gun on the truck, every part that is not the gun (hull, wheels, mount) is bit-identical. The armed truck with the autocannon is 38.8k triangles in the rig (the wheeled budget is 50k).
- **Export, built (modules PR 5).** `export::render_rig` no longer assumes four wheels and no mount. Stations come from the wheel parts' axle index and side (named `f`, `m`/`m1`.., `r` plus `l` or `r`: `fl fr rl rr` on a 4x4, `fl fr ml mr rl rr` on a 6x6); a station has a steer node if it has a knuckle part; joint coordinates follow the contract (spin = station, steer = stations + k, travel = stations + steered + station, then the articulation chains in attach order). Each placed module's `Turret`, `GunPitch` and `Recoil` parts become the chain `turret_yaw` (revolute +Y) > `gun_pitch` (revolute +X) > `gun_recoil` (prismatic +Z) in the stand-in layout of `testing::box_tank()`; a second mount's chain gets `.1`. The parent of a chain is taken from the assembly, not from geometry: each part records its placement and the node that carries the socket it sits on (`Part::placement`, `Socket::carrier` and `owner`), so a gun on a ring mount's trunnion hangs from that turntable and a gun on the hull from the hull. A node's `rest` is its pose relative to its parent; mesh positions are in the node's own frame. The unarmed 4x4's rig JSON and GLB are still byte-identical to the monolith's. Oracle: forward kinematics of the exported nodes at rest reproduces the assembled geometry for every part, and the signs hold (positive yaw turns the barrel left, positive pitch raises it, positive recoil slides it back).
- **Hull regions in metres, built (modules PR 6).** The shell is cut at four landmarks (nose face, cowl, back wall of the cab, tail face) into three regions, `UtilityDims::regions_m` = (`front_m`, `cab_m`, `bed_m`), each stretched on its own to its length in metres; the margins beyond the end stations (the bumpers' allowance) keep the template's scale. The template's fractions are the cuts' positions in the lines plan (`cab_f` in the hull RON) and every `Frac` along z (stations, windows, doors, roof socket, cover) goes through one map, `ZMap::at`, so a fitting anchored by a fraction follows the region it is in: lengthen the bed and the hood, the cab, the windscreen, the doors, the hatch and the roof mount do not move, the tail and everything anchored to it move back by exactly the stretch. Without `regions_m` the map is the old (f - 1/2) L, so the 4x4 is bit-for-bit unchanged (golden untouched). `with_bed_stretch(extra_m)` builds the stretched dims; `axles_z(overhang, tandem)` places the axles with the 4x4's overhangs; the 6x6 of the pictures is `with_bed_stretch(1.2)` with a rear tandem 1.2 m apart. Tests: explicit regions equal to the template's proportions rebuild the same truck (1e-9); a 1.2 m longer bed leaves every part in front of the cab's back wall bit-for-bit where it was and moves tail-anchored parts back by exactly 1.2 m, the hull box is exactly 1.2 m longer and the roof socket stays over the hatch; the stretched six-wheeler has closed parts, clear wheels and its sill step between the first two arches.
- **Status.** `PROVISIONAL(status:geometry)`: the vocabulary and the frame convention, until FORGE and ARCH answer the interface request that follows the export step. Plan, one PR each (under 400 lines of code): done: kernel, hull and wheel modules, ring mount, weapons, export (interface request for FORGE: `docs/swarm/requests/geometry-forge-modules.md`), regions; next: (nothing in the series; the M113 uses the same sockets); export for N stations and the turret, gun and recoil nodes with exploded and swap pictures; hull regions in metres instead of fractions of the length.

## 10. Risks
- Per-vertex flags cost triangles: measured on the hood only; whole-vehicle test at step 6, fallback in the spike note.
- Welding at 1e-5 m must not merge distinct features of small chamfers (15 mm is 1500x the tolerance: fine).
- The dossier definitions (A10) are VALIDATION's; until the M998 dossier lands the test prints PLACEHOLDER with wide bands, `PROVISIONAL(C-002)`.
- `track_runs` needs ARCH, VIEWER, GODOT and FORGE; until it lands the belt is one static mesh per side (section 12).
- Windows bake and golden bits are unchecked here (Linux only).

## 11. Skins: the game garage (ARCH, owner direction 2026-10-10: three vehicles on one course, told apart at RTS distance)
FORGE's game garage has three wheeled trucks (`scout_4x4`, `mule_4x4`, `hauler_4x4`, `content/vehicles/game/`). The Mule wears `utility_4x4`; the scout and the hauler need skins of their own, with **the same joint layout** (four spins, two steers, four travels, front axle left then right, rear axle left then right) because VIEWER retargets skins by joint index.
- **A family is a template, a skin is a family plus numbers.** `truck::TruckKind` selects the template (`shapes/<id>.ron`: a lines plan and a part list for the same shell-and-anchors machinery) and the same hull module, wheel modules and export do the rest, so the joint layout is shared by construction (a test compares the exported joints of every skin with the utility truck's). `skin::Skin` is a family with its dimensions and axles (`Skin::for_id` from stand-in files `placeholder_<id>.ron`, `PROVISIONAL(C-002)`; `Skin::from_def(&VehicleDef)` from FORGE's definition: the hull box, the axle positions from the front, the track and the tyre are the definition's, the rim and lugs are the stand-in wheel's proportions at that radius). A test reads `content/vehicles/game/<id>.ron` and checks that the stand-in numbers and the generated parts agree with it (wheel diameter, track, wheelbase, clearance, box), so the picture cannot drift from the physics rig.
- **The datum is FORGE's.** The hull box sits `ground_clearance_m` above the ground and `ride_height_m = clearance + height / 2` (`w5k_forge::compile`); a skin built from a definition uses the definition's `height_m` as the box above the underside. The axles are at the definition's `from_front_m` (not symmetric about the centre: the scout's are 0.65 m and 0.85 m from the ends).
- **Scout** (`scout_4x4.ron`): 3.70 x 1.65 m, box 1.55 m above a 0.30 m clearance, 0.70 m tyres, wheelbase 2.20 m, track 1.35 m. A fictional light reconnaissance car in the jeep and Land-Rover class: a low shell with a raised hood, a thin steeply raked windscreen slab, an open tub (the walls, two seats, a bench, a roll bar and a spare wheel stand on the deck), so from the side and from above it is a low runabout with no cab. The roll bar is structure, not a fitting: it is the highest part of the box. 28.7k of 50k triangles (the wheeled budget the owner set on 2026-10-10).
- **Hauler** (`hauler_4x4.ron`): 6.00 x 2.45 m, box 2.60 m above a 0.45 m clearance (3.05 m to the roof), 1.05 m tyres, wheelbase 3.80 m, track 2.05 m. A fictional heavy cargo truck of the 5 to 7 t class: a tall, flat-faced cab-over (steeply raked windscreen, big grille, mirrors on arms, a heavy front bumper) over the front axle and a long, low, flat bed behind it (headboard, side boards, a load, an exhaust stack, fuel tanks; the tail is open), so from the side it is two boxes of very different heights. 44.4k of 50k triangles. It was first cut against the old 40k limit (38.3k: the rear bumper and tailgate, the grille slats, roof lamps, door handles and a second load were left out), and went back with the owner's 50k; the rear bumper is a fitting beyond the shell's tail face (the shell runs the full length), the tailgate stands on the end of the deck between the side boards, and the lug count of a skin built from a definition is capped at the stand-in wheel's.
- **Silhouettes.** `the_three_skins_have_clearly_different_silhouettes_and_sizes_so_they_read_at_a_distance` renders the side view of each skin at one scale (20 px per metre, ground on one row) and requires that at least 30% of the union of two silhouettes differs (scout and utility 48%, utility and hauler 56%, scout and hauler 76%), that lengths differ by more than 15% and tyre radii by more than 10%: the garage cannot converge by accident.

## 12. The tracked carrier: hull, track run and rig (ARCH, slice 2, owner approved 2026-10-10)
SLICE-2 stage B needs a tracked carrier (an M113 archetype: a fictional light armoured personnel carrier of about 11 t, five road wheels, rear sprocket, front idler, three return rollers a side, a box hull with a sloped glacis, side sponsons over the tracks, roof hatches and a ring on the roof for a commander's gun). It is built from the same module and socket kernel as the trucks, so the owner's rule holds: hull, propulsion, mount and weapon stay separate. Every number below is `ESTIMATE` (an original design in the class, bands +-15%); the real ones are FORGE's def and rig. `PROVISIONAL(status:geometry)` for names: template `shapes/carrier_tracked.ron`, skin id `carrier_tracked` until FORGE names its def.
- **Where the numbers come from: the physics rig, not a copy of its rule.** A truck's axle positions are in its def, so `Skin::from_def` could rebuild them; a tracked def says only how many road wheels there are and how big, and FORGE's compile decides where every wheel sits. If GEOMETRY re-derived the layout the two could drift (a wheel drawn 3 cm off the one that carries load), so the skin is built from the compiled rig: `Skin::from_rig(&PhysRig, &VehicleDef)` reads every station (kind, side, hub position, radius, width, `bump_dir`) and the tracks (loop order, pitch, thickness, sprocket teeth), and puts a wheel of the right kind exactly there. Hull dimensions come from the def as for the trucks. What GEOMETRY asks FORGE for is in `docs/swarm/requests/geometry-forge-tracks.md`.
- **Modules.** The hull module is the shell (a lofted lines plan, section without wheel arches: the lower hull between the tracks, the sponsons above them), its fittings (hatches, vision blocks, lamps, towing eyes, a splash vane, the rear ramp lines) and its sockets: the roof `Ring` (the same 0.90 m ring mount and guns as on the truck, nothing new), one `Station` socket per wheel the rig has (size = that wheel's radius, `station` = the rig's station index, so a wheel's parts inherit the right joint) and one new `Run` socket per side (kind `Run`, size = belt width, on the track centre line). Wheel modules per kind (`road_wheel`, `sprocket`, `idler`, `return_roller`) mount on the `Station` sockets; the **belt module** (one per side, a part of role `Track`, which the contract calls "the belt of one side") mounts on the `Run` socket and is generated from the wheel circles. Swap the belt (link style, width) or the wheels and the hull does not change.
- **The belt path is a rubber band round the wheels.** Take each wheel the loop touches as a circle in the side plane (radius to the belt's mid-thickness line; the sprocket's is its pitch radius `p / (2 sin(pi / n))` for n teeth, because its teeth grip the pins) and stretch a band round them: straight tangent segments between neighbours and an arc on each circle. That is the convex hull of the circles; return rollers sit with their tops on the straight top run, so they touch it and add a zero-length arc. Closed form for the perimeter: sum of the tangent lengths (sqrt(d^2 - (r1 - r2)^2) for two circles d apart on the same side) plus r times the turning angle at each circle; test A11 checks it against numerical integration of the path, and that every circle the rig puts in the loop really touches the band (a roller placed too low would not, and the test says which).
- **Links tile the belt.** Perimeter L, design pitch p: n = round(L / p) links, effective pitch p' = L / n (within 1% of p or the layout is wrong), link k at arc length (k p' + phase) mod L with phase = sprocket pitch radius x spin. That is the "motion path" of an animation package: instances distributed by arc length along a closed curve, each oriented by the tangent. A link is a pad (thickness t, width = the track's), two end connectors at the pin line, a centre guide horn between the road wheels' two discs and, for a steel track, a grouser; about 80 to 100 triangles. The static belt (this slice's first picture) is the n links at phase 0 merged into one mesh per side, the stand-in until the contract can animate them: `track_runs` (CCR text in `docs/swarm/requests/geometry-ccr-shapes-and-tracks.md` section (b), refined in the new request) lets VIEWER place instances along the path from the wheel nodes' current poses, so the belt follows the suspension and the sprocket drives it. Known simplification: the pins of a real track sit a fixed chord p apart, so on the sprocket the arc spacing is up to 1.4% larger (chordal action, the polygon effect); the model uses equal arc spacing.
- **Joint layout** (the contract's `PhysRig::joint_names()`): a spin per station, a travel per station (a rigid station's travel is a spare coordinate, as in `box_tank()`), then the articulation chains of any mount; no steering. Ten stations a side is 20 stations, 40 coordinates, plus 3 for a gun on the roof ring. Per station the node chain is `<station>.travel` (role `SuspensionArm`, prismatic along the rig's `bump_dir`, vertical for road wheels and rollers, horizontal for the idler's tensioner) > `<station>.wheel` (role `RoadWheel`, `Sprocket`, `Idler` or `ReturnRoller`; revolute about -X, positive = rolling forward) and one jointless `Track` node a side, as in `box_tank()`; `w5k_replay::skin::retarget` matches skin and physics rigs by joint index and kind, so a test exports the skin and compares the joints with `joint_names()`.
- **T1, built (`track.rs`, `shapes/placeholder_carrier_run.ron`, `shapes/track_link.ron`).** `Belt::round(circles)` is the taut band (convex hull) of the wheel circles in loop order, walked counter-clockwise: for each pair of neighbours the tangent that leaves one and arrives at the other (outward normal angle `atan2(dy, dz) - acos((r1 - r2) / d)`), an arc on each circle, closed-form length; a wheel that would turn the band the wrong way (the total turn is not one full turn) is refused by name. `tile(L, p)` gives n = round(L / p) links of pitch p' = L / n; `belt_mesh` places the links by arc length, each one a pad, two connectors, a guide horn and a grouser (five plain boxes, 60 triangles: the flag-baking rows that make a bevelled truck part cost hundreds of triangles are not worth it on a 3 cm part). `run_parts(spec, link, detail)` gives one side as parts: road wheels and the idler (two rubber-rimmed discs with a gap for the guide horn, a web and a hub), the sprocket (two toothed discs, n teeth on the pitch circle, a web and a hub), the return rollers, and the belt (role `Track`, pose the track centre line). The stand-in run (5 road wheels, 3 rollers, belt 10.84 m, 71 links of 152.7 mm) is 14.1k triangles a side at detail 1. `w5k geometry sheet run` draws it.
- **T2, built (`carrier.rs`, `shapes/carrier_tracked.ron`, `shapes/placeholder_carrier_tracked.ron`).** The carrier hull is `TruckKind::Carrier`, a template of the same machinery as the trucks: a lines plan of eight-vertex sections (the narrow lower hull between the tracks under the full-width upper hull whose sides stand over them, the sponsons; `shell` takes this section when there are no wheel arches), a glacis of about 43 degrees to the front deck, the roof stepping up over the troop compartment, a vertical rear face, hatches, lamps and an antenna anchored to the shell, and the roof `Ring` socket of the trucks. `carrier::carrier_hull(dims, run, detail)` adds the running gear's sockets (`track::run_sockets`: a `Station` per wheel of both sides, size the wheel's radius, `station` its index in the loop; a `Run` socket on each track centre line, size the belt width) and `carrier::tracked_assembly` attaches `track::wheel_module` to every station and `track::belt_module` to every run; the left side is the mirror of the right, made by `attach`. The same `ring_mount` and `gun_module` that fit the truck's roof fit the carrier's (test), and attaching them leaves every other part bit-identical. Stand-in box 5.0 x 2.7 x 1.85 m, clearance 0.43 m (`PROVISIONAL(C-002)`).
- **T3, built (`skin.rs`, `export.rs`, `budget.rs`).** `Skin::from_rig(&PhysRig, &VehicleDef)` builds the carrier from the compiled rig: the hull box is the definition's; every wheel is exactly where its station puts it (`rest_pos_m`), with the station's radius and width; the belt's thickness, pitch and tooth count are the track's; the loop is oriented by where the idler is relative to the sprocket (a front sprocket's loop is reversed); and the rig is refused, with the reason, if it is not mirror-symmetric, has no belt thickness or tooth count, gives the sprocket a radius that is not the pitch radius of its teeth, or places a wheel so that the band would cut through it (`Belt::round` samples the band every 5 mm and checks every wheel clears it: the contract's own stand-in tank has all its hubs at one height, so its top run would cut through the road wheels, and it is refused until the idler and sprocket are raised). Where the drawn belt disagrees with the rig's numbers without being impossible (belt length by more than 3%, the straight ground run against `contact_length_m` by more than 5%, the ride height by 1 cm) `TrackGear::notes` says so. `export::render_rig_with` takes what the rig knows and parts do not (`Overrides`: the travel axis of every station, so an idler's horizontal tensioner moves along the hull, and the joint count, so an unarmed skin of an armed rig leaves the articulation coordinates unbound): per station `<l|r>_<idler|spr|r<k>|rr<k>>.travel` (role `SuspensionArm`, prismatic) > `.wheel` (the wheel's own role, revolute about -X), spin index = station, travel index = stations + station, no steering, and one jointless `Track` node a side; `Skin::rig(detail, flags)` is `Skin::parts` plus this. `Skin::for_id("carrier_tracked")` is the stand-in carrier (stations left side first, each side front to back, as in `testing::box_tank()`). `budget.ron` gains `tracked_triangles` (80,000, counting every link of a static belt); the stand-in carrier exports 37.5k.
- **T4, built (`track.rs`, `export.rs`, `carrier.rs`, `skin.rs`, the CLI).** The belt as the contract's `track_runs` (0.3.0, the types as I proposed them): `Skin::rig_instanced(detail, flags)` exports each side's belt as ONE link (`track::link_module`, in the contract's link frame: x along the travel, y out of the belt, z across it; symmetric across the belt, 122 vertices once baked) on the `Track` node, which sits at the hull origin so a viewer works in the hull frame, with a `TrackRun` per side: `wheels` in loop order (each wheel's spin node and path radius: tip plus half the belt thickness, the sprocket's pitch radius), `links` n = round(L / p), `sprocket` and `sprocket_joint` (the rig's spin coordinate of that station), `direction` +1 (loops are counter-clockwise, so a forward spin runs along them; a front-sprocket rig is reversed to that order, and `from_rig` already gives the right station ids). `Skin::rig` still draws the belt as one static mesh and no `track_runs`, the form a glTF can carry (`w5k geometry export carrier` writes both a JSON and a glb; `--links` writes the instanced JSON only). The link's flags are baked alone. `track::link_frames(run, centres, spin)` and `track::place_link` are the viewer's job in Rust: the tests place the exported link from the exported data and get the static belt back vertex for vertex (both sides), check the sign and size of the ground run's and top run's motion for a spin (`direction`, `R spin`), that no link enters a wheel when the idler's tensioner is pulled, and that the instanced carrier is cheaper by exactly `2 (n - 1)` links. `w5k geometry belt` draws four frames of it (`media/carrier-belt-frames.png`). What is not done, and is not mine: the packed skin (`w5k_replay::skinpack`) does not carry `track_runs` yet (request `geometry-viewer-trackruns.md`).
- **Bake quality (ARCH, for the Workshop).** The ray count was already per call (`FlagParams::cavity_rays`, taken by `Skin::rig(detail, &FlagParams)` and `export::render_rig`); now it has a name: `FlagParams::with_cavity_rays(n)` and `FlagParams::preview()` (`preview_cavity_rays` in `shapes/flags.ron`, 16 rays: VIEWER timed the hauler at detail 0 on a release build at 4.9 s for 256, 1.4 s for 64 and 0.4 s for 16). A test shows the meshes and edge flags are bit-identical and the cavity differs by sampling noise only (0.04 a vertex, 0.02 in the mean).
- **Budget and cost.** Tracked 80k triangles with instanced links counted once (ARCH, brief); the static belt counts every link, about 65 links x 2 sides x 90 = 12k, the wheels about 5k a side, the hull about 20k: about 45k. The wheels and links are the big spenders, so a link LOD is the first thing to try.
